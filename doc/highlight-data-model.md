# 高亮数据模型

## 三层职责

| 模型 | 用途 | 身份与内容 | 是否直接保存 |
| --- | --- | --- | --- |
| `ScannedHighlight` | 本次源文件提取结果及搜索索引 | `scanKey`、当前文本、位置、原始标记长度、颜色、上下文 | 否 |
| `HighlightRecord` | 仓库缓存和持久数据 | 永久 `id`、`kind`、最近定位信息、评论及时间 | 是，经 v2 编解码 |
| `HighlightView`（原 UI 名称 `HighlightInfo`） | 卡片、编辑器、搜索和 Canvas 展示 | 卡片 `id`、可选 `recordId`、源数据、评论副本、界面状态 | 否 |

`HighlightContent` 只定义可共享的内容与定位字段，不定义任何身份。

`scanKey` 由文件路径、位置和文本生成，只是临时定位及卡片键。它不是永久身份。展示数据在关联存储记录后使用该记录的 ID，并通过 `recordId` 明确标识持久关联。首次保存成功前，UI 不发布永久 ID。

## 保存流程

1. 提取和浏览只生成扫描、展示对象，不为无批注高亮建立存储记录。
2. `HighlightManager.addHighlight` 是评论保存入口：在写入队列中查找已有记录；同一高亮的两个首次保存可基于完整扫描结果复用已建立的关联。
3. 首次存储分配独立 ID；更新已有记录保留原 ID 和创建时间。生成 ID 不依赖路径、文字或位置。
4. `createHighlightRecord` 显式投影允许持久保存的字段，并复制评论；仓库不会保存调用方的 UI 对象引用。
5. 保存成功后，再更新调用方的 `id`、`recordId` 和评论快照。失败时保留未保存状态，可重试。
6. 创建闪卡先调用 `ensureStoredHighlight`，再使用返回记录的 `id` 作为 `sourceId`。已有记录不会仅因再次创建闪卡而被重写；保存失败不创建闪卡。

文件评论的记录类型为 `kind: 'file-comment'`，正文高亮为 `kind: 'highlight'`。文件评论不参与正文高亮匹配，不依赖显示文字判断类型。UI 仍使用 `isVirtual` 控制原有布局。

## 兼容性

磁盘格式保持 `version: '2.0'`。文件映射、记录键、评论 ID 和闪卡 `sourceId` 不迁移、不重建。

`decodeHighlightRecord` 把旧 `isVirtual` 转换为内存中的 `kind`；`encodeHighlightRecord` 继续写回兼容的 `isVirtual` 字段。读取旧数据不会触发自动写盘。

新 ID 使用浏览器 UUID；不支持该 API 时使用独立随机值和序列兜底。旧的路径/位置派生 ID 原样保留，新扫描不再生成这种永久 ID。

## 匹配、回写与界面

第一轮的一对一匹配、上下文计算预算、未定位记录保护继续生效。身份独立不会消除源文件定位中的歧义；完全相同的重复段落仍可能需要后续人工关联。

定位回写只提交字段补丁，读取仓库最新记录后合并，不替换评论或修改其时间。扫描来源通过弱引用及 Symbol 元数据保留，普通对象展开可继续使用完整扫描结果；JSON、磁盘和 DOM 数据快照不会包含这些引用。

搜索和 Canvas 标记、文件图标、卡片键、原始标记长度等只留在 UI 或扫描层。批量选择优先获取活跃卡片对象，避免从旧 DOM 快照取到首次保存前的临时键。卡片首次保存或创建闪卡后会更新 DOM 快照。

## 验证

- `npm run test:models`：扫描不写盘、模型边界、草稿隔离、并发首次保存、旧数据兼容、重命名、文件评论、闪卡来源与失败重试。
- `npm run test:matching`：重复文本、编辑偏移、过期扫描、并发回写和匹配性能。
- `npm run test:storage`：存储备份、损坏保护、写入顺序和生命周期。
- 其余颜色、回归、密钥和 AI 测试，以及 `npm run build`。

性能测量使用本机内存样本，不代表真实 Obsidian 界面或移动端耗时；真实应用验证应包含首次评论保存、批量创建闪卡和多窗口切换。
